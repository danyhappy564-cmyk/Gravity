# Gravity 0.2 클라이언트 플러그인 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 0.1 서버 모드에 BepInEx 클라 플러그인을 더해 공장·미궁 PMC, 봇 프로필 정리, 맵 동시 상한, "동시에" 그룹 제한, 스캐브, 무한 보충, 근처 보충, 레이드 보고를 게임에 반영한다.

**Architecture:** 순수 계산(지점 고르기·그룹 제한·스캐브 일정·판 비교)은 `Gravity.Shared`(Unity·EFT 참조 없음)에 두고 xUnit으로 시험한다. 클라 플러그인은 게임 함수 몇 개에 하모니 패치를 걸어 "판단"만 바꾸고, 봇 생성은 바닐라 경로(`BotBossSpawn`·`BotsController.ActivateBotsByWave`)에 맡긴다. 서버와 클라는 SPT 정규 라우터 3개로 이야기한다.

**Tech Stack:** 서버 C# .NET 10 + SPTarkov.* 4.1.0(기존). 클라 netstandard2.1 + BepInEx 5 + Harmony + SPT 클라 DLL(`spt-common`·`spt-reflection`) + `Assembly-CSharp`(게임 `E:\SPT 4.1`에서 참조, 저장소에 넣지 않음). 공용 netstandard2.1. xUnit 2.9.3.

**Spec:** `docs/superpowers/specs/2026-11-09-gravity-0.2-client-design.md` (0.1 설계 `2026-11-09-gravity-skeleton-spawn-design.md`도 유효)

## Global Constraints

- 클린룸: ABPS·APBS·MOAR·Donuts는 읽고 원리만. 코드·데이터·문구 복사 금지(MIT 코드 포함). 게임(EFT·SPT) API를 부르는 것은 허용.
- ORBIT 호환: 봇을 지우지(despawn) 않는다. 봇 행동 경로를 건드리지 않는다.
- ABPS(플러그인 GUID `com.acidphantasm.botplacementsystem`)가 있으면 클라 스폰 패치·프로필 정리를 걸지 않는다. 서버는 0.1처럼 잠근다.
- 게임 스레드 대기 금지, 매 프레임 지점 계산 금지. 패치마다 try/catch → 예외 시 바닐라 경로. 같은 예외 로그는 한 번만.
- 커스텀 맵(서버 `MapCatalog`에 없는 맵)·`original=false` 맵·서버 설정을 못 받은 레이드는 클라도 손대지 않는다.
- 숫자 설정은 서버에서 Clamp해서 보낸다(0.1 `ConfigModel` 방식). 클라는 받은 값을 그대로 쓴다.
- 화면·로그 글 한국어, 이모지 금지, 제목에 "—" 금지. 로그 머리 `[Gravity]`.
- 커밋 작성자 R_F, AI 트레일러 없음, 갈래 `design/skeleton-spawn`에 로컬 커밋만. **공개 푸시 금지(사용자 확인 전).**
- PiP-Disabler는 건드리지 않는다(오류는 기록만).

## 설계 문서와 달라진 점(구현 전 확정, Task 1에서 설계 문서에도 반영)

1. 클라·공용 프로젝트 대상 = **netstandard2.1**(SPT 4.1 클라 모드 관례). 설계 문서의 net472·netstandard2.0을 바꾼다.
2. 0.1 `SpawnPlanner`는 서버에 그대로 둔다. 무한 보충에 필요한 분대 목록은 서버가 미리 만들어 `ClientRaidSettings.RefillGroups`로 보낸다(이동 비용·회귀 위험 회피).
3. 정규 라우터 경로는 `/gravity-client/hello`·`/gravity-client/raid`·`/gravity-client/report`. `/gravity/`는 웹 리스너(`GravityWeb.CanHandle`)가 통째로 가져가므로 쓰지 않는다.
4. PMC 지점은 **구역 단위**로 고른다: 레이드 시작 때 모든 후보 지점을 가장 가까운 `BotZone`에 배정해 두고, 바닐라가 구역을 차례로 돌 때 그 구역 몫에서 `PointPicker`가 고른다(봇이 자기 구역에 속하게). 핫스팟 가중은 구역 순서를 가중 섞기로 바꿔 반영한다.
5. 대기열 만료는 `BotBossSpawn.TrySpawn` 뒤 패치에서 한다: 실패(false)가 이어진 Gravity 분대가 만료되면 결과를 true(처리됨)로 바꿔 대기열에 다시 들어가지 않게 한다.
6. **0.3으로 미루는 칸**(웹 띠에 계속 "다음 판"으로 남김): `spawn.hotspotBoost`(생성 시점엔 분대 크기를 바꿀 수 없고, 서버는 어느 분대가 핫스팟에 나올지 모름), `spawn.hotspotIgnoreCap`, `scav.playerScavRemain`, `scav.lateRaiders`, `near.useDefault`(맵 기본 거리값의 출처가 아직 없음). 설계 문서 4.3·4.5·4.7의 해당 문장을 이 판단으로 고친다.

## Review Focus

1. 플레이어가 PMC 후보 지점 전부 근처에 있는 작은 맵(공장) → 75% 완화 뒤에도 없으면 빈 결과, 예외·무한 재시도 없음(Task 4 테스트 `Pick_NoValidPoint_ReturnsEmptyWithReason`).
2. 레이드 시작 직후 보호 시간 안 → 보호 반경 안 지점은 절대 안 고름(Task 4 테스트 `Pick_StartProtection_ExcludesRadius`).
3. 대기열 만료 경계: 대기 179초는 유지, 180초는 버림, 하드 스톱 지난 뒤 첫 실패는 바로 버림(Task 5 테스트 `Expiry_Boundaries`).
4. 서버는 있는데 클라 판 번호가 다름(0.1 서버 + 0.2 클라 등) → 클라는 아무 패치도 안 걺(Task 1 테스트 `Compatible_MajorMinorMismatch_False`).
5. 상한이 이미 찬 상태에서 스캐브·근처 보충 차례 → 0을 돌려주고 대기열에 쌓지 않음(Task 8 테스트 `Scav_AtCap_ReturnsZero`, Task 10 테스트 `Near_StopAtCap_ReturnsZero`).
