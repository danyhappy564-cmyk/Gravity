# Gravity 0.2 설계: 클라이언트 플러그인 (2026-11-09)

> **상태: 초안, 사용자 미승인.** 1.0 로드맵(사용자 11-09 "1.0 내기 전까지 피드백 안 받음")에 따라 Claude가 정한 결정은 **[검토 필요]**로 표시했습니다.
> 참고 모드(ABPS·APBS·MOAR·Donuts)는 **읽고 원리만** 확인했습니다. 코드·데이터·문구는 가져오지 않고 새로 씁니다.
> 근거 문서: 0.1 설계 `2026-11-09-gravity-skeleton-spawn-design.md`(특히 5.4·7·11절), 결과 보고 `docs/reports/2026-11-09-0.1-result.md`, kb 2.17·2.33·2.62.

## 1. 목표와 범위

**목표**: 0.1에서 서버만으로 안 되던 것을 클라이언트 플러그인으로 해결하고, 웹 화면의 "다음 판(클라이언트 필요)" 띠를 걷어 냅니다.

| # | 기능 | 웹 설정(목업 state) | 0.1에서 안 된 이유 |
|---|---|---|---|
| F1 | 서버 연결·잠금 | — | 클라가 없음 |
| F2 | 봇 프로필 정리 | (설정 없음, 항상 켬) | ABPS를 대신하면 kb 2.17 방어가 사라짐 |
| F3 | 맵 동시 봇 상한 | `maps[id].cap` | 4.1 클라는 상한을 클라 설정 `MaxBotsAliveOnMap`으로 정함 |
| F4 | PMC 스폰 지점 선택(공장·미궁 포함) | `maps[id].pmcDist`, `spawn.spacing`, `spawn.protect`, `spawn.placement`·`hotspot*`, `spawn.allowPmcLabyrinth` | 공장·미궁은 클라 PMC 구역이 0개 |
| F5 | 그룹 개수 제한 "동시에 살아 있는" | `spawn.groupCap.scope='alive'` | 서버는 살아 있는 봇을 모름 |
| F6 | 스캐브 관리 | `spawn.scav.*`, `maps[id].scavDist`, `maps[id].start.scav` | 웨이브 밖 자동 스폰(`NonWavesSpawnScenario`) |
| F7 | 무한 보충 방식 | `maps[id].style='infinite'`, `maps[id].inf.*` | 0.1은 촘촘한 웨이브로 흉내 |
| F8 | 근처 보충 | `near.*` | 플레이어 위치가 필요 |
| F9 | 레이드 보고(진단) | 진단 페이지 | 계획과 실제를 비교할 수단이 SlopBridge뿐 |

**0.2에서 하지 않는 것**: 보스 구역·호위 수·새 맵(0.3), 특수 봇·이벤트(0.3), 팩션 모드(0.4), 장비(0.5), ORBIT 연동 옵션·프리셋·variant 구분(0.6), Fika(1.0 이후 검토). **[검토 필요]** 근처 보충의 `near.custom`(레이더·로그 섞기)은 역할만 바꾸면 되므로 0.2에 넣되, 보스급 역할은 막습니다.

## 2. 큰 구조

- **새 프로젝트 2개**
  - `src/Gravity.Client` — BepInEx 플러그인(`BepInEx/plugins/Gravity/Gravity.Client.dll`), SPT 4.1 클라 참조, netstandard2.1(SPT 4.1 클라 모드 관례).
  - `src/Gravity.Shared` — **순수 계산 라이브러리**(netstandard2.1, Unity·EFT 참조 없음). 지점 고르기·일정·그룹 제한 규칙을 여기에 두고 xUnit으로 시험합니다. 서버(net10)와 클라(netstandard2.1)가 같은 DLL을 씁니다. **[검토 필요]**
    - 이유: 0.1에서 `SpawnPlanner`를 순수 함수로 둔 덕에 테스트 39개로 대부분을 잡았습니다. 클라 로직도 같은 방식으로 게임 밖에서 시험합니다.
- **클라는 "판단"만 새로 하고 "생성"은 바닐라에 맡깁니다.** 봇 프로필 생성·분대 묶기·적대 관계는 게임 함수를 그대로 씁니다. ABPS는 PMC 그룹 생성까지 통째로 다시 짰지만(약 470줄), 바닐라에 이미 "지점 목록을 받아 그 자리에 생성"하는 경로가 있어 그럴 필요가 없습니다(4.3절). **[검토 필요]**
- **서버 없이 클라만 있거나, 클라 없이 서버만 있을 때**도 깨지지 않아야 합니다(3절).

### 2.1 단위 나누기

| 단위 | 위치 | 하는 일 |
|---|---|---|
| `ClientLink` | Client | 메뉴 진입 때 서버에 인사(판 번호), 레이드 시작 때 이번 레이드 설정 받기, 끝날 때 보고 보내기 |
| `ConflictGuard` | Client | ABPS 클라 플러그인이 있으면 스폰 관련 패치를 걸지 않음(서버 잠금과 같은 기준) |
| `ProfileSanitizer` | Client | F2 |
| `CapPatch` | Client | F3 |
| `PmcPointPatch` | Client | F4·F5 |
| `ScavDirector` | Client | F6·F7 |
| `NearDirector` | Client | F8 |
| `RaidRecorder` | Client | F9: 역할별 생성·사망·탈출 수, 대기·버림 수, 이유 |
| `PointPicker` | Shared | 후보 지점 + 플레이어·봇 위치 + 규칙 → 고른 지점(순수) |
| `AliveGroupRule` | Shared | 살아 있는 그룹 크기 목록 + 규칙 → 허용/대기/버림 |
| `ScavSchedule` | Shared | 활동·휴식 창, 여유 자리, 플레이어당 한도 → 이번에 넣을 수 |
| `ClientRoutes` | Server | `/gravity-client/hello`·`/raid`·`/report` |

> **구현 전 확정으로 달라진 점**
> 1. 클라·공용 프로젝트 대상은 netstandard2.1입니다(위 net472·netstandard2.0 표기를 고침).
> 2. 0.1 `SpawnPlanner`는 서버에 그대로 둡니다. 무한 보충에 필요한 분대 목록은 서버가 미리 만들어 `ClientRaidSettings.RefillGroups`로 보냅니다.
> 3. 정규 라우터 경로는 `/gravity-client/hello`·`/raid`·`/report`입니다.
> 4. PMC 지점은 구역 단위로 고릅니다. 레이드 시작 때 모든 후보 지점을 가장 가까운 `BotZone`에 배정하고, 바닐라가 구역을 차례로 돌 때 그 구역 몫에서 `PointPicker`가 고릅니다. 핫스팟 가중은 구역 순서를 가중 섞기로 바꿔 반영합니다.
> 5. 대기열 만료는 `BotBossSpawn.TrySpawn` 뒤 패치에서 합니다. 실패가 이어진 Gravity 분대가 만료되면 결과를 true(처리됨)로 바꿔 대기열에 다시 들어가지 않게 합니다.
> 6. `spawn.hotspotBoost`·`spawn.hotspotIgnoreCap`·`scav.playerScavRemain`·`scav.lateRaiders`·`near.useDefault`는 0.3으로 미룹니다(4.3·4.5·4.7절 해당 문장을 고침).

## 3. 서버 ↔ 클라 연결

- **경로**(SPT 정규 라우터로 등록, 클라는 SPT `RequestHandler`로 호출) **[검토 필요]** `/gravity/`는 웹 리스너(`GravityWeb.CanHandle`)가 통째로 가져가므로 `/gravity-client/`를 씁니다.

| 경로 | 보내는 쪽 | 내용 |
|---|---|---|
| `/gravity-client/hello` | 클라 → 서버 | 클라 판 번호, ABPS 클라 감지 여부. 서버는 세션별로 "클라 있음"을 기억 |
| `/gravity-client/raid` | 클라 → 서버 | 맵 id → 이번 레이드에 쓸 값(맵 설정 + 0.1 계획 요약 + 시드). 서버가 `GenerateLocationAndLoot` 때 만든 계획을 그대로 돌려줌 |
| `/gravity-client/report` | 클라 → 서버 | 레이드 끝 보고(F9). 서버는 `api/lastraid`에 계획과 나란히 보관 |

- **판 맞추기**: 서버·클라 판 번호의 앞 두 자리(0.2)가 다르면 클라는 스폰 패치를 끄고 경고 한 줄만 남깁니다. 웹에도 표시합니다.
- **경우별 동작**

| 서버 | 클라 | ABPS | 동작 |
|---|---|---|---|
| 있음 | 있음 | 없음 | 0.2 전체 |
| 있음 | 없음 | 없음 | 0.1 그대로(서버 PMC만). 웹에 "클라 플러그인 없음: 공장·미궁 PMC·스캐브·상한·근처 보충 꺼짐" 표시. 공장·미궁 PMC 항목은 넣지 않음(쓸모없이 대기열만 쌓이므로) |
| 있음 | 있음 | 있음 | 서버 스폰 잠금(0.1과 같음) + 클라 스폰 패치 안 걺. 프로필 정리도 ABPS 것이 있으므로 끔 |
| 없음 | 있음 | — | 클라는 인사 실패 → 아무 패치도 걸지 않음 |

- **스캐브를 Gravity가 관리할지**는 서버가 "이 세션에 클라가 있음"을 알 때만 켭니다. 클라 없이 스캐브 웨이브만 바꾸면 0.1 11-3에서 본 대로 넘칩니다.

## 4. 기능별 설계

### 4.1 F2 봇 프로필 정리

- 원리(kb 2.17): 봇 생성 중 `Profile.GetAllPrefabPaths`가 외형 번들 경로를 모읍니다. 클라가 모르는 외형 ID면 null이 들어가 `ConvertResourceInfo`에서 봇 생성이 통째로 실패합니다.
- **처리**: `Profile.GetAllPrefabPaths` 앞에서
  - 몸·다리·머리·손 외형 ID를 클라 외형 목록에서 찾지 못하면 그 진영(USEC/BEAR/스캐브)의 기본 외형으로 바꿉니다.
  - 장비 중 모델(Prefab)이 없는 아이템은 빼냅니다.
  - 바꾼 것은 `[Gravity] 프로필 정리: <봇 역할> 외형 <ID> → 기본` 형식으로 한 번씩만 로그에 남깁니다(같은 ID 반복 금지). 원인 모드 추적용입니다.
- 봇 프로필에만 적용합니다(플레이어 프로필은 건드리지 않음).
- **ABPS가 있으면 끕니다**(같은 함수에 같은 일을 두 번 하지 않음). APBS만 있을 때는 켭니다.

### 4.2 F3 맵 동시 봇 상한

- 원리: `LocalGame`이 PvE 오프라인에서 `BackEndConfig.Config.MaxBotsAliveOnMap`으로 상한을 정하고 `BotsController.SetSettings(maxCount, …)`를 부릅니다(4.1 디컴파일 `LocalGame.cs` 174행 부근).
- **처리**: `BotsController.SetSettings` 뒤에서 상한을 `maps[id].cap`으로 바꾸고, 봇 생성기와 구역 이탈 관리자에도 같은 값을 알립니다.
- 상한에는 보스·호위가 포함됩니다(웹 설명과 같음).
- 커스텀 맵, `original=false` 맵, 서버 설정을 못 받은 경우에는 바꾸지 않습니다.

### 4.3 F4 PMC 스폰 지점 선택 **[검토 필요]**

**바닐라 경로**(디컴파일 `BotBossSpawn.TrySpawn`):
1. PMC면 `AvailableZonesPmc`(PMC 지점이 있는 구역)에서 후보 구역을 고릅니다. 비어 있으면 `can't find zones`로 버립니다 ← 공장·미궁.
2. 구역마다 `SpawnSystem.SelectAISpawnPoints` → PMC는 `GetPmcSpawnPoints`(kb 2.33)로 지점을 받습니다.
3. 지점이 모자라면 실패 → `DelayBossSpawn` → 3초마다 재시도(시간 초과 없음).
4. 지점이 있으면 리더와 호위를 그 지점들에 생성합니다(`SpawnBotsInZoneOnPositions`, 호위는 `TryToSpawnInZoneAndDelay(…, pointsToSpawn)`).

**Gravity 처리(방식 A, 권장)** — 1·2·3단계만 바꾸고 4단계는 바닐라:
- (1) **PMC 구역이 0개인 맵**(공장·미궁)에서는 PMC 후보 구역을 "그 맵의 모든 봇 구역"으로 채웁니다. 실제 지점은 (2)에서 Gravity가 고르므로 구역은 생성 위치를 담는 그릇일 뿐입니다.
- (2) Gravity가 관리하는 PMC 분대이면 `GetPmcSpawnPoints` 대신 `PointPicker`가 지점을 고릅니다.
  - **후보 지점**: 맵의 모든 스폰 지점 중 **플레이어용 지점**(사람 스폰 자리)을 먼저, 모자라면 봇 지점까지. 공장·미궁은 플레이어용 지점만으로도 충분한지 인게임에서 셉니다.
  - **거리 규칙**: 살아 있는 플레이어·PMC와 `maps[id].pmcDist` 이상, 스캐브·보스와 `spawn.spacing.bots` 이상, 다른 분대가 방금 잡은 지점과 `pmcDist` 이상. 지점 판정 범위 안에 누가 서 있으면 제외.
  - **시작 보호**: 레이드 시작 뒤 `spawn.protect.sec`초 동안은 플레이어 `spawn.protect.radius` 안 지점 제외.
  - **분대 묶기**: 첫 지점을 정한 뒤 나머지는 그 지점에서 20m 안의 지점. 모자라면 첫 지점을 겹쳐 씁니다(바닐라와 같은 처리).
  - **핫스팟**: `spawn.placement`가 `hotspot`·`mixed`면 맵 핫스팟 구역의 지점에 가중치를 줍니다(`hotspotShare`). 핫스팟 목록은 웹 맵 설정(`maps[id].zones`)의 가중치를 씁니다. `hotspotBoost`(인원 한 단계 늘리기)와 `hotspotIgnoreCap`은 0.3으로 미룹니다(생성 시점엔 분대 크기를 바꿀 수 없고, 서버는 어느 분대가 핫스팟에 나올지 모르기 때문).
  - 거리를 만족하는 지점이 없으면 거리를 75%로 줄여 한 번 더 찾습니다.
- (3) **자리가 없을 때 정책**: 지점을 못 찾으면 바닐라처럼 대기열에 넣되, **하드 스톱 시각이 지나거나 대기 3분을 넘기면 버립니다.** 버린 분대는 F9 보고에 이유와 함께 셉니다. (바닐라는 영원히 재시도 → 0.1 세관 첫 판의 대기열 16개.)
- **"Gravity가 관리하는 분대" 구분**: 서버가 넣은 항목의 역할이 `pmcUSEC`/`pmcBEAR`이고 그 맵을 Gravity가 관리 중이면 해당합니다. 0.1 11-7과 같은 기준입니다. 출처 표시(`SptId="gravity"`)가 클라까지 오는지는 구현 첫 단계에서 확인하고, 온다면 그 값으로 바꿉니다.
- **미궁**: `spawn.allowPmcLabyrinth=false`(기본)이면 서버가 미궁 PMC 계획을 만들지 않습니다. 켜면 공장과 같은 방식으로 나옵니다.

**방식 B(대안)**: `TrySpawn`을 통째로 대체해 생성까지 직접 합니다(ABPS 방식의 원리). 방식 A의 (1)이 바닐라 다른 곳에서 막히면(예: 구역 이탈 관리자가 그 구역을 막음) B로 갑니다. 첫 구현 단계에서 공장 한 판으로 판가름합니다.

### 4.4 F5 그룹 개수 제한 "동시에 살아 있는"

- `scope='alive'`이면 분대가 생성되기 직전(4.3의 (2))에 지금 살아 있는 Gravity PMC 분대의 크기 목록을 세어 `AliveGroupRule`로 판정합니다.
- 규칙을 넘으면: 생성 시점에는 이미 프로필이 만들어져 있어 분대를 나눌 수 없습니다. 그래서 `over='split'`·`'drop'` 모두 **"자리가 날 때까지 대기"**로 처리하고, 4.3 (3)의 만료 정책을 따릅니다. **[검토 필요]** 웹의 `split` 설명에 "동시에 기준에서는 기다림"을 덧붙입니다.
- 분대가 줄어든(일부 사망) 경우 살아 있는 인원 수로 크기를 다시 셉니다.

### 4.5 F6 스캐브 관리 **[검토 필요]**

- **서버**(클라가 있는 세션만): 0.1에서 만들어 두고 쓰지 않던 스캐브 계획 중 **시작 스캐브**(`maps[id].start.scav`, `scav.separateStart`·`scav.delay`)만 `Waves`에 넣습니다. 바닐라 `assault` 웨이브는 지웁니다. 저격 스캐브(`marksman`)는 `scav.startMarksman`이 켜져 있으면 남깁니다.
- **클라**: 웨이브 밖 자동 스폰 `NonWavesSpawnScenario.Update`를 Gravity의 `ScavDirector`로 대신합니다.
  - 활동·휴식 창: `scav.activeMin~Max`분 켜고 `scav.quietMin~Max`분 쉽니다.
  - 한 번 시도 간격: `scav.refill`초.
  - 넣을 수: 상한 − `scav.softCap` 여유 − (살아 있는 봇 + 로딩 중 + 대기 중) 안에서 1마리씩. `scav.pending`(대기 중 허용 수)을 넘으면 넣지 않습니다.
  - 플레이어당 한도 `scav.perPlayer`, 플레이어 스캐브 확률 `scav.pscavChance`.
  - 지점: 일반 봇 구역 중 저격 구역 제외, 플레이어와 `maps[id].scavDist` 이상(`PointPicker` 공용), 시작 보호 적용.
  - 하드 스톱: 레이드 끝 `spawn.hardStop.scavPct` 전부터 넣지 않습니다.
- `scav.playerScavRemain`과 `scav.lateRaiders`는 0.3으로 미룹니다(웹 띠에는 계속 "다음 판"으로 남김).
- 생성 자체는 바닐라 `BotsController.ActivateBotsByWave`(웨이브 한 개 생성)를 씁니다.
- **먼 봇 지우기(despawn)는 하지 않습니다.** ORBIT 고스트 모드가 먼 봇을 관리하므로 겹치면 위험합니다(ORBIT 호환 필수 원칙).

### 4.6 F7 무한 보충 방식

- 0.1의 "촘촘한 웨이브" 대신, 서버는 `style='infinite'` 맵에 시작 분대만 넣고 클라 `ScavDirector`가 같은 루프에서 PMC도 보충합니다.
  - `inf.delay`초마다 `inf.batch`명을 넣되, 그중 `inf.pmcShare`%는 PMC(4.3 지점 규칙)·나머지는 스캐브.
  - 상한이 차 있으면 넣지 않고 다음 차례를 기다립니다(대기열에 쌓지 않음).
  - `inf.jitter`%만큼 간격을 흔듭니다.
- PMC 보충은 `BossLocationSpawn` 항목을 클라에서 만들어 `ActivateBotsByWave`로 넘깁니다(분대 크기·진영·난이도는 서버 계획과 같은 비율, 시드는 서버가 준 값).

### 4.7 F8 근처 보충

- `near.on`이면 레이드 시작 `near.firstDelay`초 뒤부터 `near.interval`초마다 한 번 시도합니다.
- 한 번에 `near.waveMin~waveMax` 자리를 보고 자리마다 `near.slotChance`%로 채웁니다. 그중 `near.pmcChance`%는 PMC, 나머지는 스캐브(또는 `near.custom` 역할).
- 지점: 플레이어와 `near.minDist~maxDist` 사이, 서로 `near.spacing` 이상. `near.sight`가 켜져 있으면 플레이어 눈에서 보이지 않는 지점만(레이캐스트). 못 찾으면 `near.attempts`번까지 다시 찾고, 안 되면 그 차례는 건너뜁니다.
- `near.stopAtCap`이면 상한이 찼을 때 시도하지 않습니다.
- `near.group`: 스캐브를 `near.group.chance`%로 `min~max`명 무리로. `scavOff`면 스캐브 무리는 만들지 않습니다.
- `near.useDefault`: 0.3으로 미룹니다(맵 기본 거리값의 출처가 아직 없음).
- 생성은 4.6과 같은 바닐라 경로입니다.

### 4.8 F9 레이드 보고

- 레이드 끝(`GameWorld` 해제 직전)에 `RaidRecorder`가 서버로 보냅니다.
  - 역할·진영별 생성 수, 분대 수와 크기, 대기·버림 수와 이유(지점 없음·상한·그룹 제한·만료), 프로필 정리 횟수, 시점별 살아 있는 수(1분 간격)
- 서버는 이것을 0.1 계획 요약과 나란히 `api/lastraid`에 두고, 웹 진단 페이지에 "계획 vs 실제" 표로 보여 줍니다.
- 인게임 검증에서 SlopBridge 감시 스크립트(`monitor.ps1` 등)가 하던 대부분을 이 보고로 대신합니다. 브리지는 원인 조사 때만 씁니다.

## 6. 처음부터 막는 함정

- 0.1 7절 전부(게임 스레드 대기 금지, 0이 무한대가 되는 값 금지, 커스텀 맵 무시, 예외는 바닐라로 되돌림).
- **패치마다 try/catch**: Gravity 판단에서 예외가 나면 그 호출은 바닐라 경로로 넘깁니다. 같은 예외는 한 번만 로그.
- **대기열 만료 필수**(4.3 (3)): 바닐라 보스 대기열은 시간 초과가 없어서, Gravity가 만든 항목이 영원히 남으면 0.1 첫 판과 같은 상황이 됩니다.
- **지점 예약**: 여러 분대가 같은 프레임에 같은 지점을 고르지 않도록, 고른 지점을 잠깐(10초) 예약 목록에 둡니다.
- **매 프레임 계산 금지**: 스캐브·근처 보충은 정해진 간격으로만 돌고, 지점 후보 목록은 레이드 시작 때 한 번 만들어 둡니다.
- 로그는 레이드당 요약 위주. 분대마다 줄을 남기는 자세한 로그는 설정 `dev`(웹 개발 페이지)에서만.

## 7. 시험

- **단위 테스트**(`Gravity.Shared` → xUnit): `PointPicker`(거리·시작 보호·예약·75% 완화·분대 묶기·핫스팟 가중), `AliveGroupRule`, `ScavSchedule`(창·여유 자리·플레이어당 한도·하드 스톱), 판 번호 비교.
- **빌드**: 서버 net10 + 클라 net472 Release. 클라 참조는 `E:\SPT 4.1`의 관리 DLL(저장소에 넣지 않음).
- **인게임**(SlopBridge, 설치 전 백업, 시험 동안 ABPS를 빼고 끝나면 되돌림 — 0.1과 같은 절차)
  1. 세관: 최종 DLL로 PMC 재확인 + 스캐브 수·상한 + F9 보고가 서버에 남는지
  2. 공장: PMC가 계획대로 나오는지(0.1은 0명) — 방식 A/B 판가름
  3. 미궁: `allowPmcLabyrinth` 켜고 PMC
  4. ABPS를 되돌린 상태: 서버·클라 둘 다 잠기는지, 레이드가 ABPS 그대로인지
  5. 프로필 정리: APBS 모드 옷 허용 상태에서 `ConvertResourceInfo` NRE 0, 정리 로그 확인
  6. 근처 보충·무한 보충: 세관 한 판씩(근처 보충은 거리·시야 규칙)
  7. `errors.log`·LogOutput 확인(PiP-Disabler 오류는 별건으로 기록만)
- 다른 맵(삼림·해안·리저브 등)은 1.0의 13맵 자동 레이드에서 봅니다.

## 8. 구현 순서(계획 문서에서 자세히)

1. `Gravity.Shared` 분리(0.1 `SpawnPlanner` 포함) + 클라 틀 + 서버 연결 경로 + 판 맞추기 + ABPS 감지
2. F2 프로필 정리(가장 작고, ABPS 없이 시험할 때 필수)
3. F3 상한
4. F4·F5 PMC 지점(세관 → 공장 → 미궁)
5. F9 보고(이후 검증을 쉽게 하기 위해 여기서)
6. F6 스캐브 → F7 무한 보충
7. F8 근처 보충
8. 웹: "다음 판" 띠 걷기, 클라 상태 표시, 진단 "계획 vs 실제"

- 큰 작업이 아닌 단위(1·2·3)는 Claude가 직접, 4·6·7은 Codex 검토를 붙입니다(0.1과 같은 방식).
- 예상: 실작업 12~18시간(인게임 판 수에 크게 좌우).

## 9. 정한 것 목록(1.0 때 한 번에 검토)

1. 순수 계산은 `Gravity.Shared`로 분리해 서버·클라가 같이 쓴다.
2. 클라는 판단만 하고 생성은 바닐라 함수에 맡긴다(PMC는 방식 A, 막히면 B).
3. 서버↔클라 연결은 SPT 정규 라우터 3개(`hello`·`raid`·`report`).
4. 클라가 없는 세션은 0.1 그대로, 스캐브는 관리하지 않는다.
5. 공장·미궁 PMC는 플레이어용 스폰 지점을 우선 쓴다.
6. 자리가 없는 PMC 분대는 하드 스톱 또는 대기 3분에서 버린다.
7. "동시에" 그룹 제한을 넘으면 나누기·버리기 설정과 관계없이 기다린다.
8. 스캐브는 서버 시작 웨이브 + 클라 자동 스폰 대체. 먼 봇 지우기는 하지 않는다.
9. 무한 보충·근처 보충은 클라 루프에서 바닐라 `ActivateBotsByWave`로 생성한다.
10. 근처 보충의 레이더·로그 섞기는 0.2에 넣되 보스급 역할은 막는다.
11. 레이드 끝 보고를 서버에 보내 웹 진단에서 계획과 비교한다.
