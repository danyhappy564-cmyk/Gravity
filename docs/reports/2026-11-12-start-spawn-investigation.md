## 1. 고정 시작 스캐브 인원이 0명으로 바뀌는 경로

공개판 계획기는 시작 스캐브 인원을 각 웨이브에 고정값으로 씁니다. 제보 프리셋과 시드로 공개판 계획기를 실행하면 보고서와 동일한 두 웨이브가 나옵니다.

| 계획 시각 | 최소 | 최대 | 분류 |
|---|---:|---:|---|
| 0~30초 | 5 | 5 | 시작 스캐브입니다. |
| 77~107초 | 5 | 5 | 시작 스캐브입니다. |

게임은 `LocalGame.ModifySettings`(레이드의 봇 양 설정을 일반 웨이브에 반영하는 부분)에서 인원을 다시 계산합니다. 로컬 게임 DLL에서 확인한 As Online/Medium 계산은 다음과 같습니다.

```text
계산된 인원 = 정수로 자름(0.5 + 중간 양 계수 × (최대 - 최소) / 2)
최소 5, 최대 5 → 차이 0 → 결과 0명
```

중간 양 계수가 어떤 정상 값이든 최소와 최대가 같으면 결과는 0명입니다. 이후 `BotSpawner.ActivateBotsByWave`(일반 웨이브를 생성하는 부분)는 인원이 0이면 바로 종료합니다.

근거는 `src/Gravity.Server/Spawn/SpawnPlanner.cs:160`, `src/Gravity.Server/Spawn/RaidSpawnApplier.cs:69`입니다. 게임 쪽 근거는 보관된 디컴파일의 `EFT/LocalGame.cs:275`, `EFT/BotAmountExtensions.cs:50`, `EFT/BotSpawner.cs:385`이며, 같은 계산과 호출을 현재 로컬 DLL의 IL에서도 확인했습니다.

이 고정 인원 전달 방식은 로컬 `v1.0.0` 태그에도 있습니다. 시작 스캐브 Count 방식 추가로 처음 생긴 문제는 아닙니다. 다만 제보자가 실제로 선택한 게임의 봇 양 설정과 추가 패치는 원본 로그 없이 확정하지 않았습니다.

## 2. 인원 계산을 통과해도 다중 구역 문자열이 실패합니다

`RaidSpawnApplier.Zones`(허용한 구역 이름을 만드는 부분)는 구역을 쉼표로 이어 붙이고, 그 값을 일반 웨이브의 `SpawnPoints`에 넣습니다. 제보 프리셋에서는 다음 값이 나옵니다.

```text
ZoneIDEAPark,ZonePowerStation,ZoneRoad,ZoneTrucks,ZoneCenter,ZoneCenterBot,ZoneGoshan,ZoneIDEA,ZoneOLI
```

게임은 이를 분해하지 않고 `zone.name == wave.SpawnAreaName`으로 비교합니다. 위 결합 문자열과 일치하는 개별 구역은 없습니다. 이 경로에서는 구역을 찾지 못한 뒤 그 웨이브가 종료됩니다.

별도 검사에서는 다중 구역의 일치 결과가 0건이고, 단일 구역만 넣은 대조군은 정상적으로 일치했습니다. 이 결함도 `v1.0.0` 태그에 존재합니다.

근거는 `src/Gravity.Server/Spawn/RaidSpawnApplier.cs:69,287,290`, 보관 디컴파일의 `EFT/WavesSpawnScenario.cs:185`, `EFT/BotSpawner.cs:404`입니다. 로컬 DLL의 실제 구역 비교 명령도 확인했습니다.

따라서 **게임의 봇 양을 High로 바꾸는 것만으로 해결됐다고 안내할 수 없습니다.** 인원 계산과 구역 전달 두 경로를 모두 다뤄야 합니다. 구역을 무조건 빈 문자열로 바꾸면 사용자가 꺼 둔 구역을 무시할 수 있으므로, 별도 구역 설정도 보존해야 합니다.

## 3. 남아 있는 소수 스캐브는 별도 보충 경로로 설명됩니다

시작 스캐브는 서버가 일반 웨이브로 보내고, 후속 스캐브는 클라이언트의 `ScavDirector`(시간·거리·대기를 확인해 보충하는 부분)가 넣습니다. 후자는 한 번에 단일 구역으로 1명씩 요청하므로 앞의 구역 결합 문제를 밟지 않습니다.

제보 설정의 보충 간격은 45초입니다. 일반 스캐브 방식에서는 `pending=1`이 한 번에 1명을 생성한다는 뜻이 아니라, 게임의 대기 봇이 1명을 넘으면 스캐브 시도를 멈춘다는 뜻입니다. 실제로 상한 24·점유 0인 검사에서도 대기 봇 2명을 주면 보충이 차단됩니다. 팝업의 영문 설명은 이 값을 보충 인원처럼 설명하여 혼동을 줄 수 있습니다.

대기·지점·로딩 차단을 제외한 8분 11초 일정 검사에서는 웨이브 방식 8회, 무한 보충 방식 11회의 요청이 나왔습니다. 실제 생성 수를 재현한 결과가 아니라, 순수 일정의 기준값입니다. 실제 5명만 나온 추가 차이는 대기·생성 경로를 더 확인해야 합니다.

image4에는 스캐브가 9초, 5분 27초, 6분 11초, 6분 59초, 7분 51초에 나타납니다. 이는 시작 웨이브가 정상적으로 10명을 만든 모습과 다르며, 별도 보충만 진행된 상황과 부합합니다.

근거는 `src/Gravity.Shared/ScavSchedule.cs:104,158`과 `src/Gravity.Client/Directors/ScavDirector.cs:96,271`입니다.

## 4. 이 판의 PMC 14명은 시작 12명과 후속 2명입니다

이 프리셋의 PMC 설정은 고정 10명이 아니라 10~12명 범위이며, 해당 시드에서 시작 12명이 선택됩니다. 보고서의 시작 무리 크기는 4·1·2·1·3·1명입니다.

| 무리 | 계획 인원 | image4의 실제 생성 시각 |
|---|---:|---|
| USEC 무리 1 | 4 | 1명은 1초, 나머지 3명은 4분 38초입니다. |
| BEAR 무리 2 | 1 | 1초입니다. |
| BEAR 무리 3 | 2 | 1명은 1초, 나머지 1명은 1분 50초입니다. |
| USEC 무리 4 | 3 | 1명은 1초, 나머지 2명은 14초입니다. |
| BEAR 무리 5 | 1 | 1초입니다. |
| USEC 무리 6 | 1 | 1초입니다. |
| 후속 USEC 무리 8 | 2 | 1분 50초와 1분 59초입니다. |

합계는 시작 12명과 후속 2명으로 14명입니다. 0분 표본의 PMC 6명은 시작 무리 여섯 개의 첫 1명씩과 맞습니다. **이 판은 시작 인원이 끝까지 사라진 사례보다, 분대원 생성이 뒤늦게 완료된 사례로 판단합니다.** 다른 판의 고정 10명 설정까지 정상이라고 일반화하지 않습니다.

게임의 `BotBossSpawn.SpawnBossSupports`(첫 봇 이후 나머지 분대원을 준비하는 부분)는 별도로 프로필 준비를 기다린 후 생성합니다. 기존 Gravity 인계 기록에도 장비 모델 로딩으로 시작 PMC가 늦어진 사례가 있습니다. 그러나 이번 지연이 프로필·장비 모델·지점·외부 패치 중 무엇 때문인지는 로그가 없어 확정하지 않았습니다.

## 5. 보고서의 spawned는 생성 완료 인원과 다릅니다

스캐브 `spawned.assault=6`은 보충 요청 수이며, 실제 생성 완료 콜백에서 세는 값이 아닙니다. PMC도 분대 생성 시도가 성공한 시점에 무리 전체 인원을 더합니다. 시작 스캐브 일반 웨이브의 완료 수를 별도로 세는 코드도 없습니다.

따라서 image4의 실제 스캐브 5명과 Gravity 보고서의 6명을 그대로 같은 집계라고 해석하면 안 됩니다. 보고서의 `dropped=0`도 앞의 시작 일반 웨이브 결함이 없었다는 증거가 되지 않습니다.

근거는 `src/Gravity.Client/Directors/ScavDirector.cs:318,322`와 `src/Gravity.Client/Patches/PmcTrySpawnPatch.cs:176`입니다. 향후 진단에서는 계획·요청·실제 생성 완료·실패를 구분하는 것이 필요합니다.

## 6. 타임라인 팝업의 범위 입력과 적용 범위를 재현했습니다

아래 설정 카드의 최소·최대 슬라이더에는 서로를 넘지 못하게 하는 짝 검사 정보가 있습니다. 타임라인 팝업은 두 값을 각각 독립 슬라이더로 만들어 그 검사가 없습니다.

공통 시작 스캐브를 3~6명으로 둔 후 팝업에서 최소만 10으로 바꾸면 다음 결과가 나옵니다.

| 처리 위치 | 결과 |
|---|---|
| 저장 대상 상태 | 최소 10·최대 6을 그대로 유지합니다. |
| 아래 설정 카드 | 조작 종료 후 다시 그려지면서 10~6을 표시합니다. image.png와 같은 상태입니다. |
| 웹 예상 인원 | 두 값을 작은 쪽·큰 쪽으로 정렬한 뒤 평균하여 약 8명으로 계산합니다. |
| 서버 설정 파서 | 최대를 최소 이상으로 올려 10~10명으로 해석합니다. |

일반적인 값 변경 후 아래 카드가 영구히 갱신되지 않는 현상은 이번 검사에서 재현하지 못했습니다. 조작 중에는 타임라인·견적 위주로 갱신하고 조작 종료 때 카드를 다시 그리는 구조입니다. 이번 검사는 실제 브라우저가 아닌 기존 웹 테스트와 같은 모의 DOM 환경입니다.

추가로 맵 카드의 타임라인 수치를 바꾸면 그 카드의 맵별 설정이 켜집니다. 전체 탭에서 방식 버튼을 바꿀 때도 현재 미리보기 맵의 방식만 바뀝니다. 따라서 팝업 안에서 방식은 이 맵만, 수치는 공통인 표시 자체는 가능한 구조입니다. 아래 공통 값과 비교할 때 적용 범위를 구별해야 합니다.

## 7. 기본 4분 지연과 시작 인원 분산은 별도 설계 사항입니다

기본 스캐브 시작 지연은 4분입니다. 무한 보충 방식으로 바꿔도 별도 시작 지연 값은 유지합니다. 제보 프리셋은 이를 0분으로 설정했으므로 그 판의 부족을 기본 4분만으로 설명할 수 없습니다.

또한 현재 시작 스캐브 인원은 레이드 시작 순간에 모두 넣는 인원이 아니라 **첫 활동 구간에 나눠 넣는 총인원**입니다. 제보 판에서도 10명을 0~30초 5명과 77~107초 5명으로 나눕니다. 생성 결함을 고쳐도 이 분산 설계를 그대로 두면 10명 전원이 0초에 나오는 동작은 아닙니다.
